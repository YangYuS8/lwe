# v1 版本路线图

本页记录从已发布的 v0.9.9 基线迈向 LWE v1 的维护中开发方向。发布后请删除或折叠过时版本小节；当产品范围、已验证运行时支持或发布优先级变化时，应同步更新本页。

## v1 目标

LWE v1 应成为可信赖的 Linux Wallpaper Engine 迁移应用，而不是宣称广泛运行时兼容的产品。

v1 目标包括：

- 基于 Tauri 2 和 SvelteKit 的 Linux 桌面应用；
- 由 Rust 后端负责 Workshop、Library、Desktop、Settings、兼容性、持久化和运行时集成服务；
- 以 Wallpaper Engine 创意工坊内容作为主要内容来源；
- 视频类壁纸是主要运行时目标；
- 场景类壁纸逐项验证，原生 2D 子集可实验性播放；未知特性或无效资源会阻断应用；
- 网页类壁纸可用于元数据识别和兼容性报告，尚无播放后端；
- Wayland + `niri` 是已验证桌面目标；
- 英文和简体中文用户可见文档与文案持续维护。

## 当前开发：实验性原生 2D Scene

原生场景路径读取已验证版本的场景包和未打包项目资源，定位本机原版 Wallpaper Engine 资源，在应用前准备纹理和着色器。兼容性报告和播放共用 `PreparedScene::prepare` 门控。缓存报告仅保留摘要，实际应用会重新验证当前资源。

当前子集包含固定正交图片层与受限共面 perspective 路径、受支持材质/特效、sprite/rope 粒子及事件子系统、四 pass LDR 泛光和单条 FLAC 循环图层。单图片 `TEXS0002` 粒子图集现保留序列/随机帧选择与序列帧插值；有界平面湍流、透明度/尺寸振荡和角运动已实现。Bool/slider/color/combo 选择及 combo 条件可见性共用校验与分配原子持久化。下文 Miku 路径增加空默认图片属性、有界 BC3 动画帧区域、私有历史及受限文字/字体渲染。纯标量脚本保留 CPU 路径，另一条有界 worker 添加限定的动态图片/音频生命周期。Fullscreen/passthrough 输入、`genericimage2` 0/30/31 模式与真实十六档立体声 uniform 保留已验收的 2.5D Space 路径，动态脚本消费真实 64 档 average 音频。活动/倾斜相机、parent 绑定、更广泛脚本/宿主 API、未知包装/组件、更广文字/动画形状、3D/骨骼层、多图片 TEXS、视频纹理及 HDR 继续阻断。准备成功仅允许实验性尝试；共面 perspective 映射、原引擎视觉/FFT/噪声一致性和日用就绪仍未验证。

验收记录须注明桌面、GPU、壁纸特性和真实显示器数量，检查反复应用/清除、Scene ↔ Video 切换及已保存分配恢复。多显示器隔离需要真实多显示器硬件。Wayland 与 `niri` 上的视频仍是主要运行时目标。[2026-10-09 Scene 记录](./guide.md#已记录的实验性-scene-验收)覆盖单显示器上的 `3337606455`，并保留当时 `3258032485` 的相机阻断；[2026-10-10 开发记录](./guide.md#2026-10-10-开发记录)单独追踪新版本。原引擎视觉 A/B 尚未执行。

当前 P0 API `SceneInventory::collect` 观察已建模的静态引用、包内 JSON/TEX/着色器与项目元数据、资源来源、可达与仅存在于包内的声明、纹理结构、粒子/骨骼/parent 声明及结构未知项。它把 `user`/`value` 绑定与 JS 分开，也把 HDR 与 bloom 分开。每次遍历都受资源/文档/着色器、节点/深度、报告、mip 与动画帧总预算限制；资源结构循环在分配前消耗剩余预算。预算耗尽或资源失败会形成部分报告，不产生“已支持”结论。脚本/着色器/文字正文和私有标量值不导出，未知或文字子树中看似资源的字符串也省略。PKG 范围读取与指纹使用已索引的同一 descriptor 并核验元数据一致性，不宣称文件系统不可变快照。

最终 `scene-inventory-p0.json` 覆盖 11 项（2,695,798 字节），11 个 PKG 的 SHA-256 均匹配基线。可达声明包括五个项目中的 31 处 JS、五个项目中的 20 处 puppet，三个项目存在层级声明。资源检查通过 18 个测试和 clippy，独立复核无剩余隐私/预算/指纹阻断。这些声明数量不计为已迁移项目。

P1 已实现的部分按每输出截止时间限帧，停止稳定静态/暂停时的 draw/swap/frame-callback 循环，并把当前/候选/回滚 Scene 资源计入引擎总计 512 MiB 的逻辑 RGBA 纹理/FBO/粒子 VBO 预算。临时、命名特效和泛光目标均计入，驱动开销、EGL 缓冲和视频资源除外。EGL 生命周期清理及单次初始视频加载已实现。可持久化并实时接入的 FPS/电池控制通过隔离 15 → 30 FPS 桌面服务测试，每秒约 14.70 → 29.60 次完成 swap，后端和分配未替换；有限原生 Settings/保存/重启和中文布局检查也通过。实际电池/交流电转换、VRAM/功耗、24 小时运行、十次真实休眠恢复、安装包及独立多显示器验收仍未完成。

### 后续目标：场景壁纸可以日常正常使用

以完整壁纸和普通桌面操作衡量进展。成功解码纹理、编译着色器、收到 IPC 成功响应或渲染第一帧都不足以通过验收。合格的壁纸应正确显示原有图层与动态效果，提供受支持的属性设置，经历正常桌面生命周期后仍可用，并在失败时保留上次保存的分配。

首批迁移样本为本地已检查的 11 个 Scene 项目。2026-10-09 的门控通过一个项目，并报告十个**首项阻断**：六个脚本/绑定、三个相机和一个 HDR。这些历史首项阻断不代表完整依赖清单，也不是本次扩展后的兼容数量。当时检查的 291 个 TEX 中有 286 个成功解码，剩余五个涉及 TEXS/视频。P0 有界 inventory 现会独立报告更多声明与未知项，不判定播放资格。以上历史比例都不能用于估计整个 Workshop 的兼容率。

### 创意工坊验收目标

实现目标是让 Steam 创意工坊的原始 Scene 项目走通真实 LWE Library 与 Desktop 流程。内置项目用于集中检查材质和渲染器，它们播放成功不能替代工坊验收。新增支持须进入共用的包读取、准备和运行时路径，不按壁纸 ID 写专用分支。完整样本须保留所需图层、动画、音频与交互；省略不支持的行为或把 Scene 换成录制视频不算适配完成。

下一组发现样本包含四个具有不同高级依赖的公开 Scene 项目。2026-10-10 已通过现有正版 Steam 会话取得全部原包，先收到下载完成回调，再核验实际文件。十二个原始文件合计 144,299,366 字节，SHA-256 与私有副本一致，验证期间源文件稳定；订阅集合未变。下载内容及着色器/脚本正文保持在 Git 之外。原有十一项保持为独立、固定的基线样本集。2.5D Space 首先通过有限真实引擎和原生 LWE UI 验收（当时本组 1/4），保留原始图层与特效。当时 Yakuza、Predator 和 Disbelief Y 首项阻断于更广泛的 SceneScript 要求。当前 Yakuza 扩展已通过有限原始项目 CPU/GPU 与原生 UI 检查，另通过真实私有输出采集/FFT/脚本/离屏 GPU 音频检查；Predator 与 Disbelief Y 继续超出有界子集。这些本地结果不能估计整个 Workshop 的兼容率。

下载完成、原始文件哈希、有界依赖清单及准备阻塞分别记录，与播放验收区分。每个项目最终须通过 LWE 核验实际画面、作者控件、暂停恢复、替换清除和持久化后的重启恢复；所需音频与交互单独检查。构建通过、静态清单完成或仅显示第一帧不能完成这个目标。

首个已获取样本 Yakuza 暴露了较旧的 `PKGV0009` 包。完整 30 项目录及负载范围符合现有有界目录结构；25 项 JSON 与五项纹理头均在不改变原始字节的条件下完成检查。读取器现在用相同的路径、范围、重叠和大小校验接纳这一已核验版本，并加入畸形输入回归；其他未核验版本仍拒绝。该快照中准备阻塞从包结构推进到 SceneScript，当前扩展另记录于下文。静态检查发现 64 档音频注册与动态创建图片层，因此不能用十一项作者对象推定实际运行图层数或开销。这是读取与依赖证据，不是播放支持。

Space 完成了 `PKGV0018` 目录结构核验，包含 49 项、28 个 JSON 文档及九项纹理头；这一精确版本复用读取器校验与畸形输入回归。目前它也通过共用的准备/运行时路径。包结构核验本身仍不能判断播放资格。

**2.5D Space 是本组新增工坊样本中首个完成完整路径的项目：**未修改的原包保留十个图片图层、十一个特效和二十四个 pass，包括八个 Scroll 实例、音频 Pulse/色差，以及四 pass 自定义泛光。通用泛光、HDR 与相机运动默认关闭，项目自定义泛光则保持启用。十四段原始脚本通过七十个数值属性用例，十二个原始着色器程序以 GL 130 链接成功，真实立体声 monitor 采集通过暂停/恢复与清理检查。全部二十个控件的真实编辑、保存失败回滚/重试、新进程恢复、重置、Settings 与有限全屏恢复也通过。最终有限引擎 Probe 在 30 FPS 上限下约 27.25 swap/s，暂停期间 draw/swap/callback 均为零并成功恢复。已通过的二十六项 GPU 像素比较及单独核实的音频到画面流程在 [Space 记录](./guide.md#space-2026-10-10)中单独追踪；Windows 视觉/FFT 一致性与 P1 长时间运行仍未完成。Yakuza 动态图片/音频子集现已有有限 CPU/GPU/原生 UI 验收，另通过真实私有输出采集/FFT/脚本/离屏 GPU 音频检查；当前 Miku 帧/历史工作另记于下文。

Predator 作为后续变形与资源目标：81 个对象、29 个布偶模型引用、67 个特效实例、可达动画纹理共 152 帧，以及 MP3 播放列表和音频脚本。Disbelief Y 覆盖文字/字体、层级、光标拖动、媒体事件及 38 段脚本；其已检查纹理没有 TEXS，因此仅实现动画纹理也不能使它正常工作。静态发现有边界：内置纹理的未知结构、不透明动态行为及未解释字段仍在私有报告中明确保留，不能据此证明语义已穷尽。

区分四个里程碑：

- **开发进展**：一张真实壁纸取得正确、完整的播放能力，并增加回归样本。
- **首个本机日用里程碑**：`3337606455`、`3258032485`、`3659880761` 在当前单输出 `niri`/680M 机器上通过画面对照、真实界面、长期运行、功耗与恢复验收。P3 后即可达到，不必等待骨骼支持或其他硬件。
- **扩展 2D 候选版**：明确声明的能力范围与更大的固定样本集通过下文验收。扩大显示器/GPU 支持声明时补对应硬件证据。
- **首批迁移完成**：初始 11 张全部正确播放，包括它们需要的高级特性。被阻断或静默省略图层的项目不计为迁移完成。日用里程碑可以先于这一里程碑，但必须列出确切支持范围。

### 运行时与平台决策

- 保留应用事务：准备 → 第一帧 → 提交 → 原子保存分配 → 最终确认。候选失败恢复上一输入源；过期取消不能撤销已最终确认的分配。分别报告期望分配、当前活动输入源与恢复失败。
- 根据资源诊断继续归因 100 轮测试中已观察到的 RSS 上升。CPU 准备/释放和后端停止后的 Rust 活跃字节回到小型固定基线，视频/混合模式的 RSS 上升则伴随 glibc 空闲块保留。受控 arena 子进程支持继续调查分配器保留，不构成生产内存修复或原生内存无泄漏结论。仍需覆盖 shell 缓存、驱动分配、swap/文件页和长期上界。P1 日用资源稳定性未通过，逻辑 RGBA/FBO 预算也不是 RSS 或 VRAM 上限。
- 在已有全局 Scene 预算和单项目限制之上扩展后续资源类型，同时核算两个输出和切换期间的新旧渲染器。限制解码资源、纹理、渲染目标、粒子与脚本；不为未使用的 pass 分配全分辨率临时目标。提高现有图层/pass 上限前先取得代表性测量。
- 区分不可变资源与每输出的属性状态，先验证默认值、类型、范围和绑定再求值；影响所需能力的值须进入兼容评估/缓存身份。通过已有串行原子写路径按项目/输出保存用户选择，保留无关分配。内嵌音频播放与桌面音频采集/FFT 分别作为能力实现。
- 分别验证静态、暂停、电池、全屏/遮挡、锁屏、输出断开和休眠恢复。依赖合成器的策略需有受支持的能力来源，缺失时明确说明。对照预期相位检查长期 shader 时间精度，不对全部 shader 任意取模时间。
- 广泛开放自定义脚本/着色器前，通过原型确定进程归属。脚本/模拟 worker 可向 Rust 渲染器提交受限更新，但不能隔离 GPU/上下文故障。渲染进程须定义输出/表面归属、请求代次、第一帧就绪、取消、资源传递与重启契约，保留应用事务，避免两个音频源同时活动。进程隔离不能保证恢复驱动级 GPU 故障。
- Wallpaper Engine 的 [SceneScript](https://docs.wallpaperengine.io/en/scene/scenescript/reference.html) 使用 ECMAScript 2018 与引擎 API。独立 Rust 渲染不要求自行编写 JavaScript 解释器。选依赖前先用原型评估兼容性、可中断性、宿主 API 行为和内存限制。[用户属性](https://docs.wallpaperengine.io/en/scene/userproperties/overview.html) 中的声明可以在没有全部 SceneScript 能力时支持。
- Wayland 的 [pointer 事件](https://wayland.freedesktop.org/docs/html/apa.html#protocol-spec-wl_pointer) 针对获得焦点的表面。壁纸能接收此类事件不等于其他窗口获得焦点时仍有全局光标来源。鼠标视差/交互须建立合成器专属能力路径，保留正常桌面输入，不静默伪造必要交互。

静态或暂停渲染稳定后，观察 60 秒，不能有自我维持的 draw/swap/frame-callback 循环；调整尺寸与明确的恢复仍可触发重绘。故障验收按已实现的边界注入 shader 编译、分配、swap/上下文、worker 退出和保存失败。UI 须保持响应、保留上次保存分配、显示实际活动/恢复状态，并允许后续再次成功应用。不可恢复的 GPU 故障后不能保证旧壁纸仍可见，恢复能力须单独取得证据。

## v0.9.8：后台运行时功耗画像

状态：已作为 v0.9.8 发布完成。本版本包含更低的空闲渲染工作量、带缓存的监视器发现、普通页面加载和恢复路径可复用的 Workshop/Library 热快照读取、基于 Rustls 的 Workshop HTTP，以及轻量快照来源诊断。真实桌面功耗测量仍与环境相关，不应泛化到已验证 Wayland + `niri` 设置之外。

主题：降低 LWE 后台运行时的 CPU 唤醒和不必要工作，尤其是在存在活动视频壁纸时。

问题陈述：

- 当前 engine loop 会按帧间隔唤醒，扫描活动 surface，并为已渲染输出重新注册 frame callback。
- mpv 渲染路径会在热路径检查新帧并 drain mpv events。
- 显示器发现可能在每次请求时 shell out 到 `niri msg -j outputs`。
- Library 和 Workshop 投影在较便宜的缓存视图足够时，仍可能触发完整目录刷新和兼容性评估。
- 安全扫描当前通过 Tauri Linux GTK/WebKit 栈报告 `glib` 告警。应跟踪上游 Tauri/GTK 更新路径，不要用不安全的依赖覆盖来掩盖。

交付内容：

- 记录以下场景的 idle/background CPU 唤醒和 CPU 占用基线：
  - 应用打开但未运行壁纸；
  - 一个活动视频壁纸；
  - 应用最小化/后台运行且存在活动壁纸；
  - 热缓存后的 Library/Workshop refresh。
- 增加轻量运行时诊断或日志，暴露 frame pacing、跳帧、活动 surface 数量和后端 event-loop 状态，同时不增加正常路径开销。
- 尽可能减少逐帧 engine 工作：
  - 当 mpv 没有新帧且 surface 无 resize/state change 时避免渲染；
  - 对未变化 surface 避免重复 EGL make-current/resize/swap；
  - frame callback 只绑定到可见/活动壁纸 surface。
- 通过短期缓存或显式 invalidation 降低显示器发现成本，避免频繁调用 `niri msg -j outputs`。
- 拆分便宜 snapshot 读取和昂贵 Workshop/Library 完整刷新，使页面加载和 restore 流程可复用热投影。
- 持续维护安全依赖卫生：
  - Workshop HTTP 请求使用 Rustls-backed TLS，而不是 OpenSSL-backed native TLS；
  - 跟踪 Tauri/Linux GTK 依赖更新，寻找脱离易受攻击 `glib` 0.18.x 的受支持路径。

实现说明：

- 功耗优化影响运行时，应优先采用小而可测的改动，并保持当前 `niri` 视频路径可靠。
- 功耗声明必须基于真实桌面观察。CI 可以覆盖不变量和回归，但不能证明合成器/GPU 功耗行为。
- 优化时不改变支持范围；场景和网页壁纸仍保持仅识别，除非另行实现并验证。
- 不要为了让扫描器安静而对 Tauri 的 GTK 栈做不安全 Cargo patch。只有在行为和打包仍通过验证时，才升级 Tauri 或移除受影响功能。

验收标准：

- 在已验证 Wayland + `niri` 环境记录优化前后的测量结果。
- 活动视频壁纸不回归已验证路径上的应用、清除、恢复或多显示器行为。
- 手动测量显示 idle/background 路径减少了不必要唤醒或降低 CPU 占用。
- 常规导航中，显示器发现和 Library/Workshop 加载路径避免不必要的重复完整刷新。
- Workshop HTTP 请求的 `cargo tree` 中不再出现 OpenSSL/native-tls。

不得宣称：

- 所有设备都有电池续航改善；
- 超出已验证 Wayland + `niri` 路径的合成器支持；
- 场景/网页运行时支持；
- 已在本地修复上游 GTK/WebKit/Tauri 漏洞，除非依赖图确实移动到 fixed 版本。

## v0.9.9：Wayland 能力基础设施

状态：已作为 v0.9.9 发布完成。本版本增加轻量 Wayland 能力报告、在动态壁纸运行时启动前进行门控、显式输出发现来源边界（保留 `niri` 作为已验证路径的增强来源）、协议支持与输出发现来源诊断，以及应用壳专用 WebKitGTK 启动 workaround 文档。

主题：让未来桌面兼容以 Wayland 协议能力为中心，而不是以桌面环境名称为中心。

问题陈述：

- LWE 当前已验证运行时路径是 Wayland + `niri`，但底层视频运行时更准确地说是 Wayland layer-shell + EGL/mpv 后端。
- 显示器发现目前只具体实现了 `niri msg -j outputs`，这会让输出可用性看起来像按桌面名称硬编码，而不是按能力判断。
- 其他 Wayland 合成器可能暴露足够协议来运行当前轻量运行时，但是否支持应由协议能力和真实验证决定，而不是泛化桌面环境声明。
- 某些环境（例如 GNOME/Mutter Wayland）可以通过 WebKitGTK workaround 启动应用壳，但可能不暴露动态壁纸所需的 layer-shell 协议。
- 在准备更广泛 Wayland 兼容时，LWE 不应加入 X11 运行时支持，也不应引入重型桌面环境专属依赖。

交付内容：

- 增加轻量 Wayland 能力报告，检查：
  - 是否存在 Wayland 会话并可连接显示；
  - 是否暴露 `wl_compositor`、`wl_output`、`zwlr_layer_shell_v1` 等必要 globals；
  - 动态壁纸运行时是可用、降级还是不支持；
  - 缺少必要协议时给出用户可理解的不支持原因。
- 将显示器发现重新表述为输出发现：
  - 保留 `niri` 作为已验证路径的增强输出信息来源；
  - 为稳定输出身份足够时的通用 Wayland 输出发现预留服务边界；
  - 避免把桌面环境名称作为主要运行时后端。
- 在启动运行时后端前，用能力报告门控 Desktop apply/restore 路径；缺少必要 Wayland 协议时返回优雅的不支持结果。
- 扩展诊断信息，包含 Wayland 能力数据：
  - 会话线索；
  - 协议可用性；
  - 输出发现来源；
  - 动态壁纸运行时支持状态和不支持原因。
- 记录 GNOME/Mutter WebKitGTK 启动 workaround：`WEBKIT_DISABLE_DMABUF_RENDERER=1`，并明确它只缓解应用壳启动，不代表壁纸运行时支持。
- 英文和简体中文文档保持诚实支持范围。

实现说明：

- 保持核心轻量：除非未来规划明确论证，否则不引入桌面环境专属 DBus/plugin 集成。
- v1 不规划也不实现 X11 壁纸运行时支持。
- 优先在 `lwe-engine` 中提供共享 Wayland 能力探测，因为该 crate 已拥有 Wayland client 依赖和 registry 代码。
- 合成器名称只用于诊断、已知问题提示和手动验证记录。
- 缺少 `zwlr_layer_shell_v1` 的合成器应在运行时启动前优雅失败，而不是尝试不可靠的兜底窗口。
- 在其他 Wayland 能力组合完成手动测试前，已验证路径仍是 Wayland + `niri`。

验收标准：

- 诊断信息能在当前设备显示 Wayland 能力报告。
- 当前已验证 `niri` 环境的视频应用、清除、恢复和显示器发现不回归。
- 缺少必要 Wayland 协议时，Desktop apply/restore 在启动壁纸运行时前返回清晰的不支持原因。
- 文档区分应用壳启动 workaround 和动态壁纸运行时支持。
- CI 覆盖能力报告格式和不支持门控，不依赖真实合成器。

不得宣称：

- X11 运行时支持；
- 未经明确验证的 GNOME/KDE/Hyprland/sway 运行时支持；
- 应用壳启动兼容等同于动态壁纸运行时兼容；
- 场景/网页运行时支持；
- 暴露 layer-shell 的每个 Wayland 合成器都自动完成验证。

### 日用可靠性验收（2026-10-12）

原可靠性计划使用隔离配置的真实 `DesktopService` 测试和持久记录器 `scripts/scene-reliability.py`。固定切换样本为 `2903458386`、`3659880761`、`3337606455`、`3258032485`，连续运行主样本为 2.5D Space。未来完整目标为同一后端 100 次完整 Scene → Video → Scene 往返、24 小时有实际呈现帧的场景运行，以及十次内核真实休眠恢复后分配保持且画面继续。用户已明确将物理休眠恢复移出本批，因为它会挂起 Codex；本批不执行、不计为通过，不休眠的记录使用 `--suspend-cycles 0`。时钟空档、锁屏、资源准备、mock 测试和中断片段均不计入有效运行时间。二进制、源码与输入身份、帧耗时直方图、RSS/PSS、原生分配器统计、FD/线程、DRM 指标和自有音频采集均写入本地证据。预热后 RSS/PSS 增长 64 MiB 与 30 FPS 渲染预算是明确验收限额，不扩大硬件支持声明。

独立特权脚本 `scripts/scene-suspend-cycles.py` 保留供未来明确包含物理恢复验收的任务使用：先设置自有 RTC 唤醒闹钟，再经正常 logind 休眠，保留 inhibitor 和锁屏，核验内核计数/日志并等待正常解锁和健康场景恢复，拒绝覆盖已有 RTC 闹钟或交流电断开。本批不执行该脚本。结束的记录器只能证明实际记录的目标：所需休眠次数为零不能证明物理恢复，短期冒烟或启动 24 小时任务也不算长期验收完成。
