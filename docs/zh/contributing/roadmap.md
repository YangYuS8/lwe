# v1 开发路线图

本页记录从当前 v0.6.1 发布线迈向 LWE v1 的维护中开发方向。请保持它最新：当产品范围、已验证运行时支持或发布优先级变化时，直接更新本页，而不是保留过时规划说明。

## v1 范围声明

LWE v1 应成为可信赖的 Linux Wallpaper Engine 迁移应用，而不是宣称广泛运行时兼容的产品。

v1 目标包括：

- 基于 Tauri 2 和 SvelteKit 的 Linux 桌面应用；
- 由 Rust 后端负责 Workshop、Library、Desktop、Settings、兼容性、持久化和运行时集成服务；
- 以 Wallpaper Engine 创意工坊内容作为主要内容来源；
- 视频类壁纸是 v1 唯一可运行的运行时类型；
- 场景类和网页类壁纸可用于元数据识别和兼容性报告，但除非未来实现并验证，否则不可运行；
- Wayland + `niri` 是已验证桌面目标；
- 英文和简体中文用户可见文档与文案持续维护。

## 里程碑 1：支持矩阵与产品事实

目标：让产品语义不容易被误解。视频类壁纸可在已验证路径上运行；场景类和网页类壁纸除非未来完成真实验证，否则仅可识别。

优先事项：

1. 在兼容性、本地库、创意工坊、桌面和文档之间保持一个权威共享支持策略。
2. 确保已同步视频项目报告为可运行支持。
3. 确保已同步场景项目报告为“已识别但运行时暂不支持”，绝不显示为可应用。
4. 确保网页项目报告为已识别/运行时不支持。
5. 明确 Library 语义：已识别本地项目可以出现在 Library，但只有可运行项目才能启用 Apply。
6. 删除或改写暗示场景运行时支持的测试和示例。

验收标准：

- 已同步视频项目报告为可用于 Library 和桌面运行时。
- 已同步场景项目报告为已识别但运行时不支持。
- 网页项目不会表现为可运行。
- Desktop apply 在调用运行时前拒绝非视频项目，并给出清晰原因。
- Library 不会为不可运行项目启用 Apply。
- 英文和简体中文文档描述同一支持矩阵。
- 测试覆盖视频、场景、网页、缺少元数据和缺少主资源行为。

主要风险：

- 支持事实可能在目录数据、兼容性策略、界面标签和文档之间漂移。
- “部分支持”如果表示“已识别”而不是“可带限制运行”，可能误导用户。
- Library 投影行为会影响用户能否检查已识别但不可运行的本地内容。

## 里程碑 2：`niri` 上可靠的视频运行时

目标：把一条运行时路径做可靠：在 Wayland + `niri` 上应用、恢复和清除视频壁纸。

优先事项：

1. 强化受支持视频项目的按显示器应用流程。
2. 强化按显示器清除行为。
3. 清除一个输出时保留其他显示器壁纸。
4. 应用启动时恢复已保存分配。
5. 在 Desktop 中展示可操作的运行时/后端失败信息。
6. 真实桌面测试保持可选，不作为 CI 必需项。

在已验证 `niri` 设备上的验收标准：

1. LWE 能发现至少一个活动显示器。
2. 用户可从 Library 应用一个已同步视频壁纸。
3. 桌面可见变化。
4. 存在多个显示器时，多显示器应用可用。
5. 清除一个显示器不会停止其他显示器壁纸。
6. 重启 LWE 后恢复已保存分配，或显示明确恢复失败信息。
7. 清除所有分配后，后续不会再次恢复。
8. 缺少 Wayland globals、EGL 失败、mpv 失败、缺少视频文件和输出不匹配都会产生可见且非泛泛的错误。

主要风险：

- CI 无法验证真实合成器行为。
- `niri` 输出 ID 和稳定显示器身份可能随会话或硬件变化。
- 后端退出或合成器状态变化时，运行时状态可能过期。

## 里程碑 3：以 Library 为中心的日常工作流

目标：让 Library 成为选择、检查、应用和管理本地内容的日常界面。

优先事项：

1. 在卡片和详情面板中清晰展示兼容性与可运行状态。
2. 仅在项目可运行且存在可用显示器时启用 Apply。
3. 在应用、清除和恢复后准确显示显示器分配状态。
4. 刷新、应用和清除后尽可能保留当前选择和详情状态。
5. 改进空状态、过期状态、不可用状态和降级状态。
6. 对大型本地创意工坊库保持可预期的过滤和分页行为。

验收标准：

- Library 清楚区分可运行视频、已识别但运行时不支持的场景/网页、缺少元数据和缺少主资源。
- 应用失败不会破坏当前 Library 上下文。
- 应用、清除和恢复后，已分配显示器标签保持一致。
- Library 测试在 CI 中不依赖本机 Steam 安装。

主要风险：

- 将已识别场景/网页放入 Library 需要强 Apply 限制和清晰文案。
- 将场景/网页排除出 Library 会让用户更难检查已识别本地内容。
- 大型 Workshop 文件夹可能暴露扫描或渲染性能问题。

## 里程碑 4：创意工坊发现与同步清晰度

目标：保持 Workshop 作为发现与获取编排，而不是 Steam 的替代品。

优先事项：

1. 清晰说明 Steam Web API key 设置。
2. 保持在线搜索和过滤可用。
3. 说明订阅、下载和同步由 Steam 负责。
4. 改进本地同步状态解释：已同步、缺少项目元数据、缺少主资源、不支持类型。
5. 保持“在 Steam 中打开”可靠并有文档说明。

验收标准：

- 缺少 API key 时给出清晰 Settings 指引。
- 在线搜索不会暗示内容已在本地可用。
- Workshop 详情会根据兼容性原因说明下一步。
- 格式错误的 `project.json` 不会导致整个本地扫描失败。
- 在线解析和类型推断测试不调用 Steam 网络 API。

主要风险：

- Steam 元数据是启发式的，可能误判类型或年龄分级。
- 用户可能期望 LWE 直接下载 Workshop 项目。
- Steam 安装路径和打包方式在不同发行版上可能不同。

## 里程碑 5：设置、持久化与诊断

目标：让用户能配置 LWE，并能提供有用的问题报告信息。

优先事项：

1. 持久化语言、主题、Steam API key、登录启动偏好和 Workshop 过滤条件。
2. 在不丢失当前上下文的情况下报告持久化失败。
3. 增加用于 issue 报告的诊断界面。
4. 隐藏 API key 等敏感值。
5. 保持英文和简体中文文案同步。

诊断信息应优先展示可观察事实而不是猜测，包括：

- 可用时显示 LWE 版本和包类型；
- 可用时显示 OS、会话和合成器线索；
- 显示器发现结果；
- 运行时后端状态或最近初始化错误；
- Steam 发现结果；
- Wallpaper Engine Workshop 路径可用性；
- 按兼容性/运行时状态统计的 Library 项目数量；
- 支持范围提醒：已验证 `niri` 路径上的视频运行时。

验收标准：

- 设置在重启后保留。
- Steam API key 不会出现在诊断或可复制日志中。
- 登录启动不可用状态可见且不会阻断应用。
- 诊断信息可复制到 issue 报告。
- Settings 测试保持确定性，不依赖桌面/会话服务。

主要风险：

- 诊断信息可能意外暴露本地路径或密钥。
- 登录启动行为随桌面、会话和包格式而变化。
- 合成器检测可能不可靠；不要夸大推测结果。

## 里程碑 6：发布强化与 v1 候选版

目标：让 v1 可以发布且便于支持。

优先事项：

1. 保持前端、文档、Rust 格式化、lint、check 和测试在 CI 中通过。
2. 验证 `.deb`、`.rpm`、`.AppImage`、AUR `lwe` 和 AUR `lwe-git` 输出。
3. 在可行时增加发布冒烟检查。
4. 保持发布说明准确陈述支持范围。
5. 对影响运行时的 v1 候选版要求手动真实桌面验收。

v1 发布验收标准：

- 英文和简体中文文档构建通过。
- 没有文档暗示场景或网页运行时支持。
- 新安装和快速开始路径有文档说明。
- 快速开始在已验证 `niri` 设备上可用。
- 视频应用、清除和恢复已手动验证。
- 不支持的场景/网页行为清楚且不可运行。
- 发布产物生成且命名符合预期。
- 已知限制已记录。

## v1 非目标

除非另行实现、测试并记录，否则 v1 不包含：

- 完整场景壁纸运行时；
- 网页壁纸运行时同等兼容；
- 创作者/编辑工具；
- 云或社区功能；
- 高级自动化规则；
- 守护进程优先架构；
- 泛 Wayland 支持声明；
- 未经真实验证的 GNOME、KDE、Hyprland、sway 或其他合成器支持声明；
- 直接替代 Steam Workshop 下载/订阅行为。

## 维护规则

- 保持用户可见行为与文档支持范围一致。
- 保持英文和简体中文文档同步。
- 涉及兼容性、导入路径、运行时行为和持久化状态的变化都应视为需要测试。
- 不要在已发布文档中归档过时规划说明；应更新或删除过时路线图内容。
